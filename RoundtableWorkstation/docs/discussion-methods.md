# Discussion methods

工作圆桌（Studio）提供项目协作、方案评审、优先级排序和多方权衡四个预设。新建圆桌时可从流程图选择预设。首席根据实际议题拟定初始议程。当前项目尚未评测这些预设是否提高答案或决策质量。

## 三类来源与证据边界

1. **多 agent 实验论文。** [Du et al., ICML 2024](https://proceedings.mlr.press/v235/du24e.html) 在所测推理与事实任务上报告多轮辩论收益；[Smit et al., ICML 2024](https://proceedings.mlr.press/v235/smit24a.html) 发现辩论并不稳定优于自洽或集成，且对协议和调参敏感；[Choi et al., 2025](https://arxiv.org/abs/2508.17536) 在七个 NLP 基准上发现多数收益可由投票解释。任务、模型、预算和协议不同，不能据此宣称“讨论必然更好”或“辩论一律无效”；本项目也未复现这些基准。
2. **人与人的小组方法。** [CDC 的 NGT 简报](https://www.cdc.gov/healthy-youth/php/program-evaluation/pdf/brief7.pdf) 使用独立写意见、轮流登记、澄清、私下排序；它产生优先表，不证明最高分方案为真。[RAND 的 Delphi 方法手册](https://www.rand.org/pubs/tools/TLA3082-1.html) 使用匿名判断、受控反馈与再次判断，建议预定轮数或稳定规则，避免为得到一致而持续加轮。我们借用分阶段和保留原判断的做法，不声称两个模型等同独立专家样本。
3. **多方公共／技术论坛。** [OECD 的市民审议流程](https://www.oecd.org/en/publications/innovative-citizen-participation-and-new-democratic-institutions_339306da-en/full-report/component-6.html) 分为学习、权衡和形成建议，可附少数报告；[审议原则](https://www.oecd.org/en/publications/innovative-citizen-participation-and-new-democratic-institutions_339306da-en/full-report/component-9.html) 强调主持独立、参与机会和决策方回应。[RFC 7282](https://www.rfc-editor.org/rfc/rfc7282.html) 要求认真处理实质异议，但不要求满足每位反对者，人数也不能代替技术理由。我们借用异议处理与追溯，不赋予模型公民代表性、民主授权或技术裁决权。

## 预设与主持

以下预设、阶段名称、默认席位与权限是本项目的实现选择，不能当作上述文献已经验证的最优配方。规则集中维护在 [internal/deliberation/policy.go](../internal/deliberation/policy.go)，界面通过预设接口读取，避免另存一套提示词。

| 预设 | 目的与阶段 | 模型编辑权限 |
| --- | --- | --- |
| `work` 项目协作 | `work`：读取项目资料、回应同伴并提出具体工作建议。可连续讨论，无需经过三个阶段。 | 仅读取项目文件。 |
| `review` 方案评审 | `proposal` 提出方案、依据和验收条件；`challenge` 检查假设、反例与证据缺口；`synthesis` 汇总可接受部分、待验证项和未解决异议。 | 可读资料，不写项目文件。 |
| `prioritize` 优先级排序 | `proposal` 明确候选及排序依据；`challenge` 检查标准、可比性与遗漏；`synthesis` 给出有理由的顺序并保留条件和分歧。 | 可读资料，不写项目文件。 |
| `forum` 多方权衡 | `proposal` 展开受影响方、利益与选项；`challenge` 检查代价、冲突和遗漏声音；`synthesis` 提出有条件的折中并记录少数意见。 | 可读资料，不写项目文件。 |

手动模式下，主持人每次发送执行一轮所选阶段。四种既有预设均可勾选「持续推进」，默认关闭。持续推进开始后，轮次仍按选定预设和阶段执行。三个分阶段预设的席位共享议题和既有历史，各自只见此前已完成的公开发言，同轮席位的发言彼此隔离。这种顺序可以减少直接跟随，模型判断仍可能相关。

### 持续推进

创建圆桌时可一起设定持续推进的目标、验收条件和轮数。创建后首席按原流程起草议程，持续推进从主持人点击开始时运行。默认轮数上限为 12，可设为 1–60；每 4 轮生成一次摘要，摘要间隔可设为 2–12 轮。压缩后，模型收到阶段摘要和最近的公开发言，较长发言使用节选。所有原话均可按轮次与席位取回核查。

每轮由复核席根据目标、验收条件和可核对的证据决定下一步。项目协作在验收通过后可以完成，三种分阶段预设在收束阶段通过验收后可以完成。需要人作决定、连续两轮没有新进展、达到轮数上限或模型调用／摘要生成失败时会暂停。会议仍保持开放，主持人仍可检查讨论、修改议程或继续手动发起。若要整理成会后报告，主持人自愿点击「完成会议」以走原有报告流程。

会中「停止」用于暂停持续推进。应用重启后只恢复已保存的会议及其进度，不自动重放或续跑；主持人明确发起后才继续。自动运行的每一轮按所选预设仅读取项目文件。未启用持续推进的会议和旧会话保持手动逐轮行为。

## 观点记录与原话核查

议程附近的「讨论观点」只由成功完成的公开发言更新。新增观点必须取自该发言原文；对已有观点表态时须引用此前可见的观点。观点由应用分配会话内编号，并关联轮次、席位和模型。立场为支持、反对、附条件或未定。首次提及议题不等于支持，没有回应的席位保持未表态，不计入共识。旧会话保留原文，不会从历史文字自动推断立场。

不同席位对同一议程事项提出冲突修订时，候选保存在事项来源记录中，不覆盖原议程。来源区显示提出轮次、席位、拟改标题、事项类型和理由，并可回看原发言。主持人显式采用或忽略候选；采用后写入修订记录并保留旧标题和来源，忽略则移除候选。

## 会后报告与一次内部复核

结束会议后，首席起草报告，执行**一次**内部复核，再由执笔席结合复核意见修订。复核模式按席位和模型关系区分：

- `peer`：另一席使用不同模型，核对具体原话、可读性并提出修改意见。
- `same_model`：由另一席复核，但两席的模型标识相同；报告明确标记这一点。
- `self`：单席会议由执笔席另行发起一次自审请求，不称为同席复核。

报告至少引用一条公开发言，结论附可定位的原话引用及相关验收条件；系统逐段核对引用编号与原文片段，点击引用可回到相应发言。验收条件与结论在语义上是否吻合仍由执笔、复核和修订席判断，不能视为程序已证明。报告是会后整理，不替代逐轮发言和原始 Markdown 导出。结束后的会话只读，报告保存在会话中，不写入项目目录。起草、复核或修订失败时显示失败阶段并可重试；从已保存草稿或复核意见恢复，首阶段失败则根据已完成公开发言重新起草，不把未完成阶段标作完成。

## 历史记录、项目规则与长会话

无法解析的历史会话以不可读条目单独返回，并附路径和原因；同一列表的其他会话仍可用。直接读取损坏记录会报告不可读，不用空会话覆盖。Markdown 导出保留议程和人物／模型修订，并移除本机绝对路径；报告与导出记录分别访问。

项目规则可以停用。每轮保存当时生效的项目规则版本快照，后续停用或修改不改写已完成轮次。保存的旧轮次保留 `settings.allow_edits` 和已发生的变更。恢复后，新轮次均以只读方式访问项目文件。议题和每轮补充说明各自最多 12,000 个 Unicode 码点。

长会话读取支持 `If-None-Match` / `ETag`；会话未变化时返回 `304 Not Modified`，避免重复传输整份记录。模型上下文按预算带入轮次与结构化观点，需要核对时可读取具体公开发言；较大的文件和差异使用有限预览，需要时再明确读取原文件。

讨论预设约束每轮处理方式。首席按实际议题拟出至多五项初始议程。已有指定事项时，首席只补缺项。生成中暂缓开会，生成失败时可重试，也可继续开会。旧会话中的模板阶段保留原有显示及完成规则。

各席可以在公开发言时提出添加或修订事项。有效提案在成功且未取消的轮次结束时按发言顺序处理，并保留原因、来源席位和轮次。同轮对同一事项提出的竞争修订中，先应用的提案成为当前版本，其余保留为候选，待主持人采用或忽略；与其他事项重名的标题仍会被跳过。修订记录保留原先的标题和事项类型。主持人可以选择下一项、改为讨论或实施，或将事项标为完成。手动模式下由主持人发起下一轮；持续推进开启时服务按其完成与停止条件接续。

`synthesis` 未点名时由会话首席收束，也可指定本场另一席。收束者整理依据、修订立场和剩余分歧。失败或缺席的席位没有可归属的立场。收束可以提议后续讨论或实施事项。实施事项可由主持人显式发起 CLI 编辑并在软件中审核。

主持人的显式人工保存走独立文件接口和版本检查。子代理始终只读，其结果先交本席主 agent 审核，不冒充另一席公开发言。

## 接口与兼容

`GET /api/studio/discussion-presets` 只读返回：

```json
{"presets":[{"id":"review","label":"方案评审","phases":[{"id":"proposal","label":"独立提案","instructions":"共享规则、场景与阶段指令"}]}]}
```

上例只展示结构，实际响应含全部四个预设及其有效阶段。读取不调用模型、不保存设置。

`POST /api/studio/sessions/{id}/run` 接受必填的 `expected_round`，以及可选的 `note`、`target`、`preset`、`phase`、`agenda_version`。省略 `continuous` 时只运行一轮。传入 `continuous` 配置时，一次启动会由服务依照复核结果接续后续轮次。请求中的轮号和可选议程版本对应当前会话快照。版本已变化返回 409。

```json
{"expected_round":1,"agenda_version":2,"preset":"review","phase":"challenge"}
```

省略预设时沿用会话和当前议程给出的默认值。实施事项默认用 `work`；旧模板事项使用所绑定的预设和阶段。其他讨论事项沿用会话预设，项目协作会话里的讨论事项默认用 `review`。既无会话预设也无当前议程的旧记录按 `work/work` 处理。显式传入预设与阶段时，应用校验组合。新轮次的 `settings.allow_edits` 均为 `false`。

配置成员的新会话创建后会异步请求首席拟议程。`GET /api/studio/sessions/{id}` 返回 `agenda_draft_status` 与已存的 `agenda`。草拟失败可向 `POST /api/studio/sessions/{id}/agenda` 提交 `action:"draft"` 重试。该接口也接受 `add`、`select`、`complete`、`reopen`。写请求须带 `expected_version`，其值来自 `agenda_version`。草拟或运行期间调整议程返回 409。轮次保存 `agenda_item_id`、`preset` 和 `phase`，这些字段随存档年代不同可能缺省或为空。

议程接口另接受 `adopt_candidate` 与 `dismiss_candidate`，需带 `item_id`、`candidate_id` 和当前 `expected_version`；采用生成 revision，忽略只移除候选，版本冲突返回 409。旧客户端仍可传 `allow_edits`，新轮次以只读执行。议题与 `note` 各自最多 12,000 个 Unicode 码点。

报告使用 `POST /api/studio/sessions/{id}/report` 的 `finish` 或 `retry` 操作；`GET /api/studio/sessions/{id}/report.md` 下载报告或带未完成标记的阶段稿。报告状态和 `review_mode` 记录在会话中。长会话 `GET` 支持 `If-None-Match` / `ETag`，未变化返回 304。具体字段和请求示例见 [接口说明](../static/api.html) 与 [OpenAPI 3.1](../static/openapi.json)。

## 指令如何进入模型请求

新项目圆桌通过本机 Magpie 网关把应用规则传入 Chat Completions 的 `system` 或 Responses 的 `instructions`。已展开的议程、项目规则副本和讨论历史作为任务上下文。设置里的「讨论规则文件」由当前版本的同一规则表生成，供在桌面查看。
